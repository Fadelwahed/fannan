## Transactional activation and rollback — after existing approvals

1. **Review record:** attach the candidate/deployment manifest digest, complete per-file Amin PASS record, Fadel's yes, runtime evidence and read-only access/branch-check proof. Any pending item blocks activation. The release approval ledger is a template of missing evidence, not pre-signed approval.
2. **Back up:** snapshot the exact live skill folders, tool tree, trust files, active caller references and memory through the approved storage/backup route. Verify checksums and record the restore operation. Archive old skills; do not delete them.
3. **Stage inactive:** prepare the full new tree, dependencies outside it, approved pinned binary and its original launcher/support assets. Run integrity, syntax, regression, token, real-browser and negative-path checks. Require an actual successful end-to-end checker run with the protected binary on the target architecture. Validate every caller and each frontmatter name.
4. **Hold execution:** use the host's supported lifecycle to stop new Fannan runs and wait for in-flight work to finish. The installer must prove this hold; a same-session sequence of shell copies is not atomic. Do not guess runtime commands or kill unrelated processes.
5. **Commit as one migration:** while held, activate the complete skill/tool tree, retire all eight old skill folders, update all callers, apply the approved memory saves and activate the corresponding external manifest/pin. Never expose the new callers with old skill names. If the host supports an atomic release switch, use its reviewed mechanism; if not, the verified hold plus complete rollback boundary is mandatory. The host mechanism is untested here.
6. **Verify before resuming:** read back names, memory, hashes and paths; run manifest verification, project prechecks, token build, checker and the existing thirteen helper tests if supplied. Any failure restores every changed member from the verified snapshot while execution stays held. Memory restoration must be proven too; a partial rollback is not success.
7. **Resume and record:** resume only after all acceptance evidence passes. Record exact versions/hashes, commands, outcomes, restoration point and task status. Report to Fadel through the approved channel. No live migration is performed by this rewrite.

### Host transaction evidence required before activation

The installer must fill one transaction record with the actual supported host API/command, concrete owner, invocation/result evidence and rollback action for each operation below. An empty field or a proposed command is not proof. These operations belong to the authorized installer, never Fannan's read-only design lane.

| Operation | Required evidence | Failure behavior |
|---|---|---|
| Hold and drain | Block new Fannan runs, list/drain active runs, read back the held state | Stay held; do not swap files |
| Snapshot complete state | Exact skill/tool/trust/caller/memory revisions, backup digest and tested restore route | Stay held; discard incomplete staging through approved archive policy |
| Stage inactive release | Verified deployment manifest, runtime and dependency inventory, pinned detector, complete caller/rename checks | Keep old release active but execution held |
| Activate complete unit | Host-supported release switch or coordinated file/caller/memory transaction under the proven hold | On any partial change, restore every member from the snapshot |
| Read back | Manifest, active skill names, caller targets, all nine memory saves, runtime and dependency IDs | Restore the complete snapshot; recheck old state before resuming |
| Recover interruption | Fault injection before swap, after file switch, after caller update, after memory update and before resume; process crash/restart cannot start a mixed state | Restart remains held until recovery completes; recovery owner is named |
| Resume | Explicit success after checks, or verified complete rollback on failure | Never automatically resume from an ambiguous or partially restored state |

No host lifecycle API or saved-memory transaction interface was supplied. This package deliberately contains no guessed installer that copies files and calls the result atomic. The candidate is one versioned bundle; live atomicity remains P1-5 until the concrete record and failure-injection results exist.

The full operation cannot honestly be called atomic on the live host until its hold/activation/rollback mechanism has been tested. The candidate is shipped as one immutable bundle so partial skill installation is not the recommended or supported path.
